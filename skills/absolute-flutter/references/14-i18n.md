# 14 — i18n: localization with intl_utils + ARB + generated AppLocalizations

Strings live in **ARB source files** (`lib/res/l10n/intl_<locale>.arb`), and
`dart run intl_utils:generate` compiles them into a typed **`AppLocalizations`**
class under `lib/generated/`. Widgets read strings as `context.s.keyName`;
non-widget code reads them as `AppLocalizations.current.keyName`. Placeholders
and ICU plurals become typed method parameters. A `LocaleChangeService` flips the
app's locale at runtime.

Read `_conventions.md` first; it is the binding contract this doc obeys. The
codegen plumbing already ships under `assets/templates/config/` (the
`flutter_intl:` block in `pubspec.partial.yaml`, the analyzer `exclude:` in
`analysis_options.yaml`) — this doc is the **usage** layer on top of it.

## When to use

Reach for this reference when the task is any of:

- Add a user-facing string (always — no hardcoded UI text).
- Add a placeholder (`{name}`) or an ICU plural/select (`{count, plural, ...}`).
- Wire l10n into `MaterialApp` for a fresh app (delegates + supportedLocales).
- Read a localized string from non-widget code (a data source, a service).
- Switch the app's language at runtime.

For where the `context.s` shortcut sits among the other BuildContext extensions,
see `10-extensions.md`. For registering the `LocaleChangeService` singleton, see
`03-di.md`. The `class_name: AppLocalizations` setting is part of the codegen
config covered in `02-dart-conventions.md`.

## Pattern (the why)

- **ARB is the source, `AppLocalizations` is the artifact.** You edit ARB; you
  never edit the generated Dart. `intl_utils` reads the `flutter_intl:` block
  from `pubspec.yaml` (class_name `AppLocalizations`, main_locale `en`, arb_dir
  `lib/res/l10n`, output_dir `lib/generated`) and emits `lib/generated/l10n.dart`
  (the `AppLocalizations` class) plus `lib/generated/intl/messages_*.dart` (one
  per locale). This keeps translations declarative and in one place, and gives
  every key a compile-checked Dart accessor — a typo in a key name is a compile
  error, not a runtime blank.
- **Typed accessors, not string lookups.** A plain key becomes a getter
  (`context.s.welcomeTitle`); a key with placeholders becomes a method
  (`context.s.greeting('Alex')`, `context.s.itemsCount(3)`). The compiler
  enforces argument count and type, so a missing placeholder is caught at build
  time.
- **`main_locale: en` is the template + fallback.** `intl_en.arb` defines the
  full key set and the `@key` metadata (descriptions, placeholder types). Other
  locales mirror the same keys with translated values; a key missing from a
  non-main locale falls back to `en`.
- **One generated class, two entry points.** `AppLocalizations.of(context)`
  resolves the instance for the widget's locale (non-null — it asserts the
  delegate is installed). `AppLocalizations.current` is the last-loaded instance
  for code that has no `BuildContext`.
- **Runtime locale switching is a one-callback rebuild, not a global rebuild
  storm.** The root App state owns the active `Locale`; a `LocaleChangeService`
  singleton holds a `void Function(Locale)?` callback the root registers. Any
  caller resolves the service and calls `notifyLocaleChanged(locale)`; the root
  `setState`s and `MaterialApp` rebuilds with the new `locale`.

## The flow: arb → generate → AppLocalizations

```
lib/res/l10n/intl_en.arb        <- you edit (main locale: full key set + @metadata)
lib/res/l10n/intl_pt.arb        <- you edit (same keys, translated values)
        |
        |  dart run intl_utils:generate
        v
lib/generated/l10n.dart         <- AppLocalizations (delegate, of, maybeOf, current, load)
lib/generated/intl/messages_*.dart  <- one per locale (gitignored + analyzer-excluded)
        |
        v
context.s.welcomeTitle          <- in a widget
AppLocalizations.current.ok     <- in non-widget code
```

The generated `AppLocalizations` exposes: `static const delegate`,
`static AppLocalizations of(BuildContext)` (non-null, asserts),
`static AppLocalizations? maybeOf(BuildContext)`,
`static AppLocalizations get current`, and
`static Future<AppLocalizations> load(Locale)`. You call `of` / `current` /
`delegate`; never the others by hand.

## Any language

The structure is language-agnostic — a locale is just another `intl_<code>.arb`
with the same key set. The demo ships `en` + `pt`, but `es`, `fr`, `de`, `ja`,
`zh`, `ar`, `he`, … are added the exact same way:

1. Add `lib/res/l10n/intl_<code>.arb` (e.g. `intl_ja.arb`) mirroring the main
   locale's keys, with translated values.
2. `dart run intl_utils:generate`.
3. Done — `AppLocalizations.delegate.supportedLocales` now includes it; no other
   code changes.

What makes it truly any-language:

- **Non-Latin scripts (CJK, Cyrillic, Devanagari, …)** need nothing special — ARB
  is UTF-8 and the generated accessors are identical.
- **RTL languages (`ar`, `he`, `fa`, `ur`)** are handled automatically: Flutter
  derives `Directionality` from the active locale, so layouts mirror without code
  changes. Prefer direction-aware widgets (`EdgeInsetsDirectional`, `start`/`end`,
  `AlignmentDirectional`) so padding/alignment flip correctly.
- **Plural categories differ per language.** ICU defines
  `zero/one/two/few/many/other`; English/Portuguese use `one`/`other`, Arabic uses
  all six, Japanese/Chinese use only `other`. Fill the arms each language needs —
  `other` is always required and is the safe fallback.
- **`/af-i18n` ASKS which languages to support** and creates one ARB per choice.
  Don't assume `en` + `pt`; the demo set is just a starting point.

## Folder placement

```
lib/
  res/l10n/
    intl_en.arb                  # main locale — full key set + @metadata
    intl_pt.arb                  # mirror locale — SAME keys, translated values
  generated/                     # intl_utils output — gitignored, analyzer-excluded, NEVER hand-edited
    l10n.dart                    #   class AppLocalizations
    intl/messages_en.dart
    intl/messages_pt.dart
  common/util/
    localization_context_ext.dart  # extension on BuildContext: `AppLocalizations get s`
  common/service/
    locale_change_service.dart     # runtime locale switching (get_it singleton)
  app_widget.dart                  # MaterialApp.router wiring (delegates/supportedLocales/locale)
```

Placement rules:

- **ARB sources → `lib/res/l10n/intl_<locale>.arb`.** The directory MUST match
  `arb_dir` in the `flutter_intl:` block.
- **Generated → `lib/generated/`.** Matches `output_dir`. Gitignored and excluded
  in `analysis_options.yaml` (`lib/generated/**`). Never edit.
- **`context.s` extension → `common/util/`**, beside the other BuildContext
  capability extensions (`10-extensions.md`).
- **`LocaleChangeService` → `common/service/`**, registered as a singleton in DI
  (`03-di.md`).

## Step-by-step: add a key

1. **Edit `intl_en.arb`** (the main locale). Add the key, its value, and the
   `@key` metadata block (a `description`, plus a `placeholders` block if it has
   placeholders or is an ICU plural).
2. **Edit EVERY other locale file** (`intl_pt.arb`, …) with the same key. Keys
   must be in sync across all locales — a key only in `en` falls back to `en` and
   never gets translated.
3. **Regenerate:** `dart run intl_utils:generate`. This rewrites
   `lib/generated/l10n.dart`. (It is a separate pass from
   `build_runner` — see `02-dart-conventions.md`.)
4. **Use it.** In a widget: `context.s.keyName`. In non-widget code:
   `AppLocalizations.current.keyName`. Import the extension file
   (`package:app/common/util/localization_context_ext.dart`) at any widget call
   site that uses `context.s`.

## Placeholders and ICU plurals

- **String placeholder.** In ARB: `"greeting": "Hello, {name}!"` with a
  `placeholders` block typing `name` as `String`. Generated as a method:
  `context.s.greeting('Alex')`.
- **ICU plural.** In ARB:
  `"itemsCount": "{count, plural, =0{No items} =1{1 item} other{{count} items}}"`
  with `count` typed `int`. Generated as `context.s.itemsCount(3)` — the `int`
  selects the `=0` / `=1` / `other` arm. The literal count inside `other` is
  `{count}` again (nested braces are intentional).
- **Always declare the placeholder TYPE** in the `placeholders` block. Without
  it, `intl_utils` defaults to `Object`/`String` and the plural selector or
  number formatting silently misbehaves. Use `int` for plural counts.
- **`select` works the same way** (`{gender, select, ...}`) — type the selector
  as `String`.

## of(context) vs current

- **`AppLocalizations.of(context)` (via `context.s`) — in widgets.** Resolves the
  instance for the widget subtree's locale. Non-null; it asserts the delegate is
  installed. This is the default; use it everywhere there is a `BuildContext`.
- **`AppLocalizations.current` — in non-widget code.** A data source, a service,
  a mapper, or an enum-label extension has no context. `current` returns the
  last-loaded instance (valid after the delegate's first `load(...)`, which
  happens during `MaterialApp` setup). It tracks the active locale, so it follows
  a runtime switch.
- **`AppLocalizations.maybeOf(context)`** returns `null` instead of asserting —
  use only when l10n may legitimately be absent (rare; the wired app always has
  it).

## The `context.s` extension

`localization_context_ext.dart` declares `extension LocalizationContextExt on
BuildContext { AppLocalizations get s => AppLocalizations.of(this); }`. Widgets
read `context.s.welcomeTitle`. This is the l10n sibling of the BuildContext
capability extensions in `10-extensions.md` — same rationale (fluent, greppable,
single sanctioned access path), and like all extensions it is **not
auto-imported**: import the file at the call site or the getter won't resolve.

## MaterialApp wiring

The root widget is the `StatefulWidget` in `app_localization_wiring.dart` (it
holds the mutable `Locale`). Compared to the stateless
`assets/templates/app_scaffold/app_widget.dart`, it adds three l10n fields to
`MaterialApp.router`:

```dart
localizationsDelegates: const <LocalizationsDelegate<dynamic>>[
  AppLocalizations.delegate,
  GlobalMaterialLocalizations.delegate,
  GlobalWidgetsLocalizations.delegate,
  GlobalCupertinoLocalizations.delegate,
],
supportedLocales: AppLocalizations.delegate.supportedLocales,
locale: _locale, // null => device locale; non-null => runtime override
```

Imports added: `package:app/generated/l10n.dart` (the generated
`AppLocalizations`) and
`package:flutter_localizations/flutter_localizations.dart` (the three
`Global*Localizations` delegates). `supportedLocales` is DERIVED from the
delegate — never hand-list locales.

## Locale switching service

`LocaleChangeService` (`locale_change_service.dart`) is the one-way channel for
runtime language switching, registered as a get_it singleton (`03-di.md`):

```dart
it.registerLazySingleton<LocaleChangeService>(LocaleChangeService.new);
```

1. The root App state, in `initState`, calls
   `AppDI.it<LocaleChangeService>().setListener(_onLocaleChanged)`, where
   `_onLocaleChanged` does `setState(() => _locale = locale)`.
2. Any caller (a settings Controller, a deep link) resolves the singleton and
   calls `notifyLocaleChanged(newLocale)`.
3. The root rebuilds `MaterialApp` with `locale: newLocale`, and every
   `context.s` / `AppLocalizations.current` now reads the new locale.
4. The root clears the listener in `dispose` to avoid calling into a defunct
   `State` after teardown / hot restart.

## Gotchas

- **Generated files are gitignored AND analyzer-excluded.** `lib/generated/**` is
  in `analysis_options.yaml`'s `exclude:` and should be in `.gitignore`. They are
  rebuilt by `intl_utils:generate`, never committed, never hand-edited. (Unlike
  the `*.freezed.dart` / `*.g.dart` siblings, which 02 commits — the l10n output
  is regenerated locally.)
- **Run `dart run intl_utils:generate` after EVERY ARB change.** It is a separate
  pass from `build_runner`. Forgetting it means `context.s.newKey` does not exist
  yet (compile error) or shows a stale value.
- **Keep keys in sync across every locale file.** A key present only in the main
  locale falls back to `en` and is never translated. Add the key to all locales
  in the same edit.
- **`class_name` is `AppLocalizations`.** It is set in the `flutter_intl:` block
  in `pubspec.partial.yaml` (`02-dart-conventions.md`). If you change it there,
  the generated class name and every `AppLocalizations.*` reference change with
  it — keep them aligned. (Some older `intl_utils` setups default the class to
  `S`; this skill standardizes on `AppLocalizations`, so use
  `AppLocalizations.current` / `AppLocalizations.of(context)`, not `S.current`.)
- **`context.s` collides with the design-system spacing extension.** The design
  system also exposes `context.s` (`AppSpacingTheme`, `context.s.md` — see
  `09-design-system.md`). Two `s` getters on `BuildContext` are **ambiguous when
  both files are imported into the SAME library** ("the property 's' is defined
  in multiple extensions"). Resolve it by importing only one per file, or
  disambiguate with explicit extension-override syntax
  (`LocalizationContextExt(context).s` vs `AppContextExtensions(context).s`). If
  both surfaces are needed app-wide, consider aliasing one (e.g. expose l10n as
  `context.l10n` instead) — but the contract here uses `context.s` for l10n, so
  keep spacing and l10n in separate import scopes.
- **`AppLocalizations.current` is null before the first `load`.** It is only
  valid after the delegate loads a locale (during `MaterialApp` setup). Reading it
  in pre-`runApp` code throws — wrap such code to run after the first frame, or
  pass strings down instead.
- **`supportedLocales` is derived, not declared.** Use
  `AppLocalizations.delegate.supportedLocales`. Hand-listing locales drifts from
  the ARB files the moment you add a locale.
- **Plurals need `int`, not `String`.** A plural placeholder typed as a string
  makes the selector compare text, not number — `=1` never matches. Type `count`
  as `int` in the `placeholders` block.
