# 03 — Dependency injection: modular get_it, two-phase ordered bootstrap

Read this when you wire dependencies: add a binding for a new layer or feature,
register a Controller/use case/repository, or fix init order. Obey
`references/_conventions.md` (package imports, neutral nouns) at all times.

## When to use

Reach for this reference whenever you:

- scaffold the DI bootstrap for a new app (the `AbstractBinding` contract +
  `AppDI` container + the two ordered lists);
- add a **feature** and need its presentation `registerFactory(() => Controller(...))`;
- add a **layer** registration (a repository, data source, service, use case,
  async DB) into the right `*_binding.dart`;
- debug a "not registered" / "used before async resolved" error, or a feature
  whose Controller never resolves because its binding was never appended.

A trivial change (rename a local var, a comment) does not need this. Adding or
ordering a registration does.

## Pattern (the why)

**One container, reached through one handle.** The locator is `GetIt.instance`,
exposed exactly once as the static `AppDI.it`. There is no second locator. Every
layer reads singletons through `AppDI.it<T>()`; the View pulls its Controller the
same way. One handle means one place to reason about lifetime and order.

**Every registration lives in a binding — never inline.** A binding is a class
extending `AbstractBinding` with one method, `Future<void> binding(GetIt it)`.
The app never calls `it.registerX(...)` in `main` or in a widget; it always goes
through a binding. WHY: the abstract contract lets `AppDI` treat all
registrations uniformly — `for (b in list) await b.binding(it)` — so the whole
wiring graph is a list you can read top to bottom.

**Bindings are grouped by architectural layer, one file each.** Core layers are
app-wide under `lib/di/<layer>/` (gateway, service, data_source, repository,
domain, mapper); env + db live beside their feature (`configurations/di/`,
`database/di/`); presentation is sliced **per feature** under
`lib/feature/<feature>/di/`. WHY: one file per layer/feature keeps merge
conflicts local and makes each slice independently readable.

**Bootstrap is ordered and two-phase.** `AppDI` holds an explicit ordered
`List<AbstractBinding>`, split so init runs in two passes:

- **Phase 1 — `setupBasicInfrastructure()`**: env → db → network → data → repo →
  domain. Runs first so logging, `Environment`, and the DB are live before
  `main` initializes any third-party SDK and before any feature registers.
- **Phase 2 — `setupRemainingBindings()`**: mappers + every feature presentation
  module. It `.skip()`s the infra prefix already registered in phase 1, so
  nothing is double-registered.

The **order in each list is load-bearing**, not cosmetic: it encodes dependency
direction. `Environment` is first because everything below it reads
`AppDI.it<Environment>()`. `Domain` is last among infra because every use case
depends on a repository registered above it. Splitting into two phases is what
lets infra come up, `main` do its SDK init against a live logger/config, and
features register afterward.

**Registration kind is chosen by layer, deliberately:**

- **data / domain / repository** → eager `registerSingleton<I>(Impl(it(), it()))`.
  Bound by **interface**, impl as the value. Eager so the wiring fails fast at
  **boot** if a dependency is missing, instead of lazily mid-session.
- **cross-cutting services cheap to defer** → `registerLazySingleton<T>(() => T())`.
- **async deps (the DB)** → `registerSingletonAsync<T>(() async => ...)`;
  consumers `await it.getAsync<T>()`.
- **presentation (Controllers)** → `registerFactory(() => Controller(it()))` so
  each screen gets a **fresh** Controller with fresh `RxNotifier` state. Promote
  to `registerLazySingleton` only for a Controller that must survive across
  screens; use `registerFactoryParam<T, P1, P2>` when runtime args are needed.

(Legacy note: older features may `registerFactory(() => SomeCubit(...))`. In
this skill the presentation object is an rx_notifier `Controller`; register the
Controller, not a Cubit.)

**Resolution shorthand.** Bare `it()` is the callable form of `it.get()` and
resolves positionally by the **declared constructor parameter type**. Use
explicit `it<T>()` / `it.get<T>()` only to disambiguate at a call site. Keep
exactly **one registration per type** — if two impls share a type, bare `it()`
silently picks the registered one.

## Folder placement

```
lib/
  di/
    abstract_binding.dart                 # AbstractBinding contract
    app_di.dart                           # AppDI: handle + two ordered lists + phased setup
    gateway/gateway_binding.dart          # network clients / interceptors glue
    service/service_binding.dart          # cache, http clients, auth, analytics
    data_source/data_source_binding.dart  # data sources
    repository/repository_binding.dart    # I*Repository -> *Repository
    domain/domain_binding.dart            # ALL use cases (one central binding)
    mapper/mapper_binding.dart            # reserved slot (often empty)
  configurations/di/environment_binding.dart   # Environment + Logger (registered FIRST)
  database/di/database_binding.dart            # secure storage + async DB
  feature/<feature>/di/<feature>_binding.dart  # one per feature: registers its Controller(s)
```

Core/layer bindings are few; feature bindings are many — all assembled in
`app_di.dart`. Use cases are **all** registered in the single `DomainBinding`
(central, easy to scan the full use-case surface; the trade-off is a hot merge
file). The mapper binding is kept as a reserved slot even when empty so mappers
have a home without restructuring the ordered list.

## Templates

Copy the matching file and rename the neutral anchors (`Example`, `Home`,
`Detail`, `Feature`, `Item`) to the real name. Do not regenerate from prose.

| File | What it is |
|---|---|
| `assets/templates/di/abstract_binding.dart` | The `AbstractBinding` contract — one async `binding(GetIt it)` method. |
| `assets/templates/di/app_di.dart` | `AppDI`: the `it` handle, the two ordered lists, `setupBasicInfrastructure` + `setupRemainingBindings` (with the `.skip()` of the infra prefix). |
| `assets/templates/di/example_layer_binding.dart` | A core **layer** binding showing the full kind mix: eager `registerSingleton<I>(Impl(...))`, `await getAsync` on the DB, `registerLazySingleton`. |
| `assets/templates/di/example_feature_binding.dart` | A **feature** binding: `registerFactory` the Controller (default), named-arg factory, `registerLazySingleton` for a long-lived Controller, `registerFactoryParam` for runtime args. |

## Step-by-step to apply

**Bootstrap a fresh app:**

1. Copy `abstract_binding.dart` and `app_di.dart` into `lib/di/`.
2. In `app_di.dart`, keep the two lists and the order: `Environment` first in
   phase 1, `Domain` last in phase 1; phase-2 list spreads the infra prefix then
   appends mappers + features.
3. Call the two phases from `main` around your SDK init:
   ```dart
   Future<void> initServices() async {
     WidgetsFlutterBinding.ensureInitialized();
     await AppDI.setupBasicInfrastructure();          // env + logger + db + net + data + repo + domain
     final Environment env = AppDI.it<Environment>(); // SDK init that needs config/logger goes here
     await AppDI.setupRemainingBindings();            // mappers + all feature modules
   }
   ```

**Add a feature:**

1. Copy `example_feature_binding.dart` to
   `lib/feature/<feature>/di/<feature>_binding.dart`; rename `Example`/the class
   to `<Feature>Binding` and `ExampleController` to `<Feature>Controller`.
2. `registerFactory(() => <Feature>Controller(it(), ...))` — bare `it()` per dep.
3. **Append `const <Feature>Binding()` to `_listOfBinding` in `app_di.dart`** in
   the features section. Without this the feature never registers — the binding
   file alone does nothing. Use grep to find `_listOfBinding` rather than reading
   the whole file.

**Add a layer registration** (repository / data source / service / use case):

1. Open the matching `lib/di/<layer>/<layer>_binding.dart` (copy
   `example_layer_binding.dart` if creating one).
2. Bind data/domain/repository by **interface**, eager:
   `it.registerSingleton<I<Name>Repository>(<Name>Repository(it(), it()));`.
   Add use cases to the single `DomainBinding`.
3. If it depends on the DB, `await it.getAsync<AbstractDatabase>()` before
   building it.
4. Confirm the layer's binding is in `_listOfBasicInfrastructure` in the right
   order (it usually already is; only new layers need inserting).

## Gotchas

- **`await it.getAsync<T>()` is mandatory for anything registered with
  `registerSingletonAsync`** (the DB). A sync `it<T>()` before it resolves
  throws. A service depending on the DB must `await it.getAsync()` in its own
  binding.
- **Order in `_listOfBasicInfrastructure` is load-bearing.** `EnvironmentBinding`
  first (later bindings and `main` read `AppDI.it<Environment>()`);
  `DomainBinding` last among infra (every use case depends on a repository).
  Intra-binding order matters too — register a thing before whatever depends on
  it inside the same `binding()`.
- **A feature binding not appended to `_listOfBinding` never registers.** The DI
  file alone does nothing; its Controller will fail to resolve at push time.
- **Bare `it()` resolves by declared parameter type.** Two impls sharing a type
  means it silently picks the registered one — keep **one registration per
  type**.
- **`registerFactory` for Controllers, not singleton.** Each screen needs a
  fresh Controller with fresh `RxNotifier` state. Use `registerLazySingleton`
  only for app-global Controller state; never default to it.
- **Eager `registerSingleton` for data/domain is intentional** — it fails fast
  at boot if a dep is missing. Reserve `registerLazySingleton` for heavyweight
  or optional cross-cutting services.
- **Preserve generated marker comments** (e.g. `//REPOSITORY_BINDING`,
  `//DATA_SOURCE_BINDING`) if a binding has them — they are codegen insertion
  points. Don't leave commented-out dead registrations to accumulate.
